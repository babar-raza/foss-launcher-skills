# Generated vs. Maintained Content

Classification guide for all content files in this repository.

Status: VERIFIED_CURRENT
Last verified: 2026-06-22
Evidence: Frontmatter patterns from live content files; AGENTS.md §5; skill contracts

---

## Classification Overview

Content files fall into four categories:

| Category | `auto_updatable` | `content_origin` | Who changes it |
|---|---|---|---|
| Auto-generated | `true` | `skill-generated` | Pipeline (regenerated freely) |
| Generated, locked | `false` | `skill-generated` | S-73 (manual-edit skill) only |
| Human-authored | `false` | `human-authored` | Humans or S-73 |
| Non-content files | N/A | N/A | Governed by path_guard.py |

---

## Auto-Generated (auto_updatable: true)

These files are produced by pipeline skills and can be regenerated whenever the underlying
knowledge changes. The pipeline will overwrite them without asking.

**Examples:**
- `content/reference.aspose.org/en/{family}/{platform}/{ClassName}.md` — generated by `/batch-reference`
- `content/docs.aspose.org/en/{family}/{platform}/{topic}.md` — generated by `/new-docs-page` or `/page-draft`
- `content/kb.aspose.org/en/{family}/{platform}/{slug}.md` — generated by `/new-kb-howto` or `/new-kb-faq`
- `content/blog.aspose.org/{family}/{platform}/{slug}/index.md` — generated by `/new-blog-post`

**Frontmatter signature:**
```yaml
provenance:
  content_origin: skill-generated
  last_mechanism: skill
  skill_id: S-XX
  auto_updatable: true
  content_hash: <hash>
```

**How to identify:** `auto_updatable: true` in the `provenance:` block.

---

## Generated, Locked (auto_updatable: false, skill-generated)

These files were created by the pipeline but have been locked against automatic regeneration.
They require the S-73 (manual-edit) skill to modify.

**Common locked pages:**
- `_index.md` section pages (structural landing pages)
- Family/platform subtitle pages
- Reference `_index.md` grouped index pages (after initial generation)

**Frontmatter signature:**
```yaml
provenance:
  content_origin: skill-generated
  last_mechanism: skill
  skill_id: S-XX
  auto_updatable: false   # ← locked
  content_hash: <hash>
```

**How to edit locked pages:**
1. Invoke S-73: `skill_context.py begin --skill S-73 --scope "path/to/file"`
2. Make the edit
3. Re-activate scope before each additional edit (scope expires per file)
4. The pre-commit hook will block edits to `auto_updatable: false` pages without an active scope

---

## Human-Authored (auto_updatable: false, human-authored)

These pages were written by humans and registered via `/register-human-content`. They are
never auto-repaired or regenerated by pipeline skills.

**Frontmatter signature:**
```yaml
provenance:
  content_origin: human-authored
  last_mechanism: human
  auto_updatable: false
```

**How to register a human-authored page:**
```
/register-human-content {file-path}
```

This sets `content_origin: human-authored` and `auto_updatable: false`, attaches evidence
based on available knowledge, and assigns a baseline grade.

---

## Non-Content Files (path_guard rules apply)

These files are not Hugo content pages. Governance rules determine who can modify them.

| Category | Example paths | Who can modify |
|---|---|---|
| Data registries | `data/products.json`, `data/families.json` | `update_product_registry.py` script |
| Hugo themes | `themes/*/layouts/`, `themes/*/assets/` | Human operator + override token |
| Hugo configs | `configs/*.toml`, `configs/*.yml` | Human operator + override token |
| Site layouts | `layouts/partials/`, `layouts/_default/` | Human operator + override token |
| Pipeline scripts | `scripts/pipeline/commands/` | Agents with appropriate skill context |
| Governance docs | `docs/governance/`, `docs/workflows/`, `docs/registries/` | Human operator + override token |

## Decision Table: How to Classify a File

Use this flowchart to determine how to treat a content file:

```
Is the file under content/ ?
├─ NO → Non-content file. Check path_guard.py allowed/forbidden paths.
└─ YES ↓

Does it have provenance.auto_updatable in frontmatter?
├─ NO → Inspect manually. Likely legacy or missing provenance. Add provenance block.
└─ YES ↓

Is auto_updatable: true?
├─ YES → Auto-generated. Pipeline can regenerate freely.
└─ NO ↓

Is content_origin: human-authored?
├─ YES → Human-authored. Use S-73 for changes. Never auto-repair.
└─ NO → Generated, locked. Use S-73 to unlock, then edit.
```

## Reference Pages: Special Case

All files under `content/reference.aspose.org/` are generated by `batch_reference.py` and
have `auto_updatable: true`. However, **the reference grouped index** (`_index.md` in each
platform directory) may be set to `auto_updatable: false` after initial generation if it has
been manually customized.

The CI check `scripts/ci/checks/check_reference_index_structure.py` enforces that reference
`_index.md` files use the grouped structure (H2 sections by namespace), not the flat
`{{< children >}}` shortcode.

## Generated Output That Must Not Be Edited Manually

These files are generated outputs. Editing them manually is **prohibited** because the
generator will overwrite the changes:

- `content/reference.aspose.org/en/**/*.md` — all reference pages
- `knowledge/{family}/{platform}/merged/` — promoted knowledge artifacts (run `/truth-merge` instead)
- `knowledge/{family}/{platform}/scout/` — extraction output (run `/repo-scout` instead)
- `reports/` — pipeline evidence output (local-only; never committed), **except
  `reports/repo-presenter-regen-full/{family}/**` and `reports/plan_state/**` (the durable
  mission/taskcard ledger, schema 5f — tracked whole-subtree, not per-name, since its child
  mission directories are unbounded and grow weekly; TC-GOV-01,
  MT071-2026-09-17-GOVERNANCE-DURABILITY-HARDENING), both deliberately tracked per the
  `git-tracking-policy` system (S-125) — see `scripts/pipeline/config/git_tracking_policy.yaml`
  and `skills/git-tracking-policy.md`. Any other future exception must be added the same
  way (a new policy entry), never by hand-editing `.gitignore`.

## Knowledge Dependency for Generation

Before any skill can generate or regenerate content, it must verify that local knowledge
artifacts are fresh:

```
knowledge/{family}/{platform}/merged/model.yaml  must exist with stale_since == null
```

If knowledge is missing or stale:
1. Run `/repo-scout {family} {platform}` to re-extract from source
2. Run `/truth-merge {family} {platform}` to promote to merged/
3. Then run the generation skill

See AGENTS.md §5a for the full knowledge bootstrap gate rules.

How this was measured

For each of the 69 original bullets, every backtick-quoted identifier and bolded term was extracted as a "salient token" (a method name, option name, or named sub-feature — the kind of thing that names a real, specific claim). Each token was then checked against the candidate's Key Capabilities + Scope and Limitations prose ("prose"), the API Reference tables ("table"), and the whole document ("anywhere"). This is a deliberately generous measure — a token counts as "covered" the moment it appears anywhere in the candidate, with no check that the surrounding explanation, defaults, or edge-case behavior came with it. Real retention is likely lower than these numbers, not higher.

What the numbers look like in real text

The worst case, in full. This is the original's single largest bullet (11.5 KB) against everything that plausibly derives from it in the candidate.

SVG embedding — page.AddSVGObject()

48% token coverage
Original — one bullet, ~1,700 words

Covers gradients (stops, gradientUnits, spreadMethod, per-stop opacity via a luminosity /SMask, separate fill/stroke masks), masks (maskUnits/maskContentUnits, the −10%/120% default region, nested masks, mask-type: alpha), markers (width/height, refX/refY, units, orient, mid-vertex tangent bisection), a full CSS cascade (selectors, specificity, !important, unsupported at-rules named individually), patterns (patternUnits, overflow="visible" growing the /BBox), images (magic-number sniffing, nested SVG capped at 4 levels), all of SVG 1.1's filter primitives named one by one plus the four exact chains that stay vector, and <textPath> glyph placement including method="stretch".

Candidate — everything that survives

One API Reference table row: "Parse an SVG and draw it into [x, y, w, h] ... linearGradient/radialGradient (→ PDF shading patterns), text/tspan, <pattern> (→ PDF tiling patterns...), <image> (...), <style> rules (...), <mask>/markers, and <filter> (all of SVG 1.1's primitives, rasterized ... except four chains ...)."

No stop/opacity semantics, no mask region defaults, no marker geometry, no named filter primitives, no CSS at-rule list, no <textPath> mention anywhere. The topic is named; almost none of the explanatory depth is.

Digital signatures — the better case, for contrast

44% token coverage, but real redistribution
Original — one bullet, ~700 words

Signing algorithms (RSA PKCS#1 v1.5/PSS, ECDSA P-256/384/521, Ed25519), credential sources (PEM, PKCS#12, external HSM/KMS callback), PAdES/CAdES subfilters, DocMDP certification levels, RFC 3161 timestamps with named helper functions, CAdES commitment types, LTV (/DSS), and a detailed VerifySignatures verification pipeline (chain trust, revocation via OCSP/CRL, padesLevel ladder).

Candidate — genuinely more complete

A dense Scope-and-Limitations paragraph covers signing paths, PAdES/CAdES, DocMDP, timestamps, LTV, and the full verification pipeline (chain trust, revocation, DocMDP enforcement) in real, connected prose — plus 8 separate API-table type rows (CommitmentType, CadesAttributes, SignerLocation, ValidationDataOptions, DocMdpPermission...). The exact algorithm list and helper function names are gone, but the shape of the capability survives better here than SVG's 48% score alone would suggest — because signing maps naturally onto named types a table can carry.

The pattern: API-surface-shaped topics (named types, options, enums) redistribute reasonably into tables. Behavior-shaped topics (exact semantics, defaults, edge cases, algorithms explained in prose) do not have a natural home in a table row and are the ones actually being lost.

05

Why my own check called this clean

check_content_unit_merged_into_target_section splits each extracted excerpt into sentence groups and requires at least one matching token per group to appear in the claimed target section. A single compressed table row containing "gradients," "patterns," "filters" and "masks" satisfies that bar for an entire 1,700-word bullet. The check was verifying "the topic is mentioned," not "the explanation survived" — a real, now-confirmed gap in how this mission verified retention, not a difference of opinion about editorial style.

How it was actually fixed

The user chose the strongest of the three options above: harden the skill itself, not just this one candidate, then regenerate and re-verify in a loop until real retention is proven — not asserted.

1. A new hard gate, portfolio-wide. check_content_unit_reframe_fidelity promotes a word-overlap fidelity score — until now a reviewer-only number buried in an on-demand report — to a real blocking check, at the same 0.5 threshold the report already used to label a row "low fidelity." A compressed table row that only shares a few keywords with a 1,700-word original bullet now fails the run outright, on every future product, not just this one. Portfolio impact measured before shipping: 2 other products (3d/net, note/python) turned up 1 genuine finding each — real, disclosed, left for their own future fix, not silently absorbed into this one.

2. The actual content, restored — not re-summarized. Hand-condensing 69 dense bullets a second time risked repeating the exact same mistake with different wording. Instead, the full original ## Features text was inserted essentially verbatim into a new, collapsed #### Detailed Capability Reference block under Key Capabilities — the same "short overview, then full detail" shape the API Reference already uses successfully for its own 360-class surface. All 71 real content units this maps to were re-verified and re-disposed accordingly (62 that were compressed, plus 8 that had been dropped for being "too granular for a bullet" — under the new rule, that is no longer a valid reason to drop something real).

3. Two small, genuine check bugs, found only because the fix made rewording impossible. Once real original text was preserved instead of paraphrased, two narrow false positives surfaced that could not be worked around by changing the wording (it isn't this skill's wording anymore) — a "dot leaders" typesetting phrase colliding with a real DOT-format registry entry, and "ONE" (a number word) colliding with itself across a bolded and a code-comment casing. Both fixed at the check level, narrowly, with tests, not by touching the content.

4. One real thing found along the way, and included. A genuine upstream commit (7b994de4, landed 2026-09-03) added a small, real capability — incremental saves — after the pinned snapshot this candidate was built from. Verified directly against the new source and folded in: an extended Saving paragraph, a new API-reference row, and a new Limitations bullet.

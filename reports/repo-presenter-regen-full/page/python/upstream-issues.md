## A Module-Import-Order Bug Breaks Several Natural Import Patterns in a Fresh Interpreter

- **Severity**: BLOCKING
- **Evidence**: `aspose.page.pdf.writer` and `aspose.page.ps` import each other at module load time (`aspose/page/pdf/writer.py` imports `aspose.page.ps.encodings`, which triggers `aspose/page/ps/__init__.py`, which imports `.output`, which imports back `from ..pdf.writer import PdfMetadata, PdfWriter, ImageResource`). A near-identical cycle exists between `aspose.page.image.raster_renderer` and `aspose.page.ps` (via `ps.ttf_outline` → the `aspose.page.ps` package `__init__` → `.output` → `.color_ops` → `.patterns` → `.text_ops` → back to `image.raster_renderer._contours_to_path`). Reproduced directly, three separate ways, in a fresh interpreter against the current `26.7` checkout (re-confirmed 2026-08-15, after `pdf/writer.py` changed substantially — 292 lines — between the `26.5.0` and `26.7` releases): (1) `from aspose.page.common.render_model import RenderModelBuilder, Matrix` followed by `from aspose.page.pdf.writer import PdfWriter, PdfMetadata` raises `ImportError: cannot import name 'PdfMetadata' from partially initialized module 'aspose.page.pdf.writer' (most likely due to a circular import)`; (2) `from aspose.page.image.raster_renderer import RasterRenderer` alone raises the mirrored error, `cannot import name '_contours_to_path' from partially initialized module 'aspose.page.image.raster_renderer'`; (3) `from aspose.page.xps.document import XpsDocument` followed directly by `doc.to_pdf()` (with no prior import of `aspose.page.ps`) raises the same `raster_renderer` variant, since `xps/output.py`'s own `to_pdf()` implementation imports `aspose.page.pdf.writer` before anything has initialized `aspose.page.ps`.
- **Impact**: any of these three natural, unremarkable import orderings — the ones a new user reaching directly for the render-model API, the raster API, or the higher-level XPS conversion method would plausibly write first — fails immediately in a fresh interpreter with a cryptic circular-import traceback, not a clear error about the library's own functionality. The real, confirmed workaround is a bare `import aspose.page.ps` before touching the render-model, PDF-writer, or raster-renderer modules directly, or before converting an XPS document straight to PDF. Two categories of usage never need this workaround, re-confirmed safe by direct execution against the current `26.7` checkout: the higher-level PostScript document conversion methods, and every helper in the repository's own MCP integration layer — both already trigger the necessary import internally, early enough in their own module's import chain to avoid the cycle.
- **Not fixable here because**: the cycle is a structural property of the upstream package's own internal module graph (two submodules each importing the other at load time) — resolving it requires restructuring the upstream package's own imports (e.g. moving the shared types the cycle depends on into a separate module both sides can import without importing each other), which is out of scope for a README refresh on a different, downstream site. The candidate README documents the real, working import-order workaround directly in every example it affects, matching the one already-shipped, already-effective mitigation.

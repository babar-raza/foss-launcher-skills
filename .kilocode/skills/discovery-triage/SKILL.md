## Purpose

Read patrol and sweep reports and create structured backlog items for every finding; routes all discoveries and upstream changes to operator-reviewed backlog items and never directly invokes S-12 or S-84 in MVP.

## IMPORTANT: Triage-First Mandate

**This skill NEVER directly invokes S-12 or S-84 in MVP.**

All findings route to backlog items. The operator reviews backlog items and manually invokes
S-84 per product. Direct S-84 dispatch is gated behind TC-GATE-01 (post-pilot rollout gate).

## When to use

After running S-93 (/repo-patrol) and/or S-94 (/change-sweep), run this skill to route
findings into the backlog.

## Pre-conditions

- `reports/discovery/patrol_report.json` exists (generated by S-93 `/repo-patrol`) **and/or**
- `reports/discovery/sweep_report.json` exists (generated by S-94 `/change-sweep`)

At least one report file must exist to proceed. The skill may be invoked with patrol-only,
sweep-only, or both reports present.

## Steps

### Step 0 (MANDATORY GATE): run the discovery health gate

A patrol report can be produced by a scan that never reached some or all GitHub orgs.
An empty `new_candidates` list from such a scan means **"we did not look"**, not
**"there is nothing new"**. Triaging it creates a backlog set that silently understates
reality — the exact failure ST-058 was filed for.

**This is a real gate, not a judgement call. Run it and obey the exit code:**

```bash
PYTHONPATH=scripts/pipeline .venv/Scripts/python \
  scripts/pipeline/commands/diagnostics/repo_patrol.py gate
```

| Exit | Verdict | Action |
|------|---------|--------|
| **0** | `ok` | Proceed normally. Findings are complete. |
| **1** | `degraded` | Proceed, but **every** backlog row created from this report MUST carry the provenance stamp the gate prints, e.g. `discovery_health: degraded (24/25 orgs, missed: aspose-zip-foss)`. Do **not** record "no new products found" as a conclusion. Recommend a re-run once the cause is cleared. |
| **2** | `blocked` | **HARD STOP.** Create no backlog rows from this report. Covers `failed`, an unrecognised status, a missing report, and a report with no `scan_health` block (predates ST-058 → health **unknown**, never assume healthy). Report the remedy from the gate's `reason` (commonly a rejected credential — use a classic PAT in `GH_TOKEN`) and re-run `/repo-patrol`. |

The full verdict, including `failures[]` and the exact `provenance_stamp` string, is
written to `reports/discovery/discovery_verdict.yaml`. Use `--json` for machine-readable
output.

Do not substitute your own reading of `scan_health` for this command: the gate exists
because the prose version of this table shipped first and was still bypassable
(MT020-L2-01 → MT021).

`sweep_report.json` has no `scan_health` block; its `fetch_failures[]` is the
equivalent signal and is already surfaced in Step 5.

1. Read the patrol report (if it exists):
   reports/discovery/patrol_report.json

2. Read the sweep report (if it exists):
   reports/discovery/sweep_report.json

3. For each entry in patrol_report["new_candidates"]:
   - action = "launch_candidate" (confidence >= 0.70): Create backlog item P1, Cat=K, Effect=KF, Size=L
   - action = "investigate" (confidence 0.40-0.69): Create INV-item P2
   - Record item in backlog/inbox.md using S-88 format

4. For each entry in patrol_report["status_changes"]:
   - change = "newly_archived": Create INV-item P2 -- "Archived repo: {family}/{platform}"
   - change = "gone_inactive": Create INV-item P3 -- "Inactive repo: {family}/{platform}"

5. For each entry in sweep_report["changed"]:
   - impact = HIGH: Create backlog item P1, Cat=K, Effect=TF -- "{family}/{platform} upstream change (HIGH)"
   - impact = MEDIUM: Create backlog item P2, Cat=K, Effect=TF
   - impact = LOW: Log in session output only; no backlog item

6. For each entry in patrol_report["unclassifiable"] that looks plausible (agent discretion):
   Create INV-item P3 -- "Unclassifiable repo: {repo_name}"

7. Set deferred discovery candidates with review date: after 30 days from today.

## MT074: Consuming the fleet ledger (keyed, duplicate-safe rows)

Added by mission MT074 (steps 1-7 above are unchanged). `/change-sweep` (S-94) now has a clone-free
fleet step (`fleet_drift.py`) that writes a `reports/discovery/sweep_report.json`-compatible file
(`--sweep-out`), so the existing Step 5 reads it with no changes. The fleet ledger adds more detail than
the sweep schema: use it to rank and key the rows.

1. **Inputs.** `reports/discovery/sweep_report.json` (fleet-compatible), plus optionally
   `reports/fleet/drift_ledger.json` (tier, `api_surface_touched`, `ahead_by`, `release_state`, ground-truth tier) and
   `reports/fleet/candidates.json` (from `propagation_analyze.py rank`: ranked candidates with capability-unit counts).
   Step 0 still applies: run `repo_patrol.py gate` and obey the exit code before creating any row. A degraded
   verdict puts the provenance stamp on every row, exactly as before.
2. **One row per product and upstream SHA, with a key.** Row key: `FLEET-PROPAGATE-{family}-{platform}-{upstream_sha8}`.
   - Priority: release-triggered candidate P1; `API_TOUCHED` P1; `SOURCE` P2; `UNKNOWN` P2 (a blind spot is never dropped); `NON_SOURCE` and `NO_CHANGE` are logged only.
   - Within a priority, order by the L4 rank when `candidates.json` exists, otherwise by `family/platform`.
   - Cat=K, Effect=TF, Size from the capability-unit count when known (otherwise `ahead_by`/files changed).
   - The row body names the next action: `/refresh-product {family} {platform} --mode upstream`, then `/example-write`, the surface skills by disposition, `/independent-content-review`.
3. **Duplicate safety (required before every write).** Search `backlog/inbox.md` and `BACKLOG.md` for the exact key. Present: do not add a row. If the existing row's facts changed (new SHA gives a new key, so a changed `tier` or `release_state` for the same key), update that row in place instead. A second run on the same ledger must add zero rows. A key for an older SHA of the same product is superseded: mark the older row `superseded-by` the new key rather than leaving two open rows.
4. **No refresh from here.** This skill does not invoke S-84 or S-12 for fleet findings, even with `--auto-refresh`
   (TC-GATE-01 does not extend to fleet rows). The refresh stays an operator-started, agent-run chain with independent verification.
5. **State is not written here.** This skill never writes `data/content_propagation_state.json`. The
   state file's drift fields come from `fleet_drift.py --update-state` (S-94) and its propagation fields only from
   `capability_surface_gate.py` (S-84 close step). A closed backlog row does not mean propagated.

## Follow-Up Policy for Deferred Candidates

Candidates deferred via backlog triage use date-based review (30 days from deferral).
They surface at session-start via the existing briefing mechanism (CONVENTIONS.md deferred review).

## Post-Pilot Gate (TC-GATE-01)

After 3 successful triage cycles with correct routing, operator may enable --auto-refresh.
With --auto-refresh and HIGH+MEDIUM count <= 3: invoke S-12 then S-84 sequentially.
With --auto-refresh and count > 3: still create backlog items.
This gate must be explicitly approved by the operator (see TC-GATE-01 in the discovery plan).

> Authority: Human maintainer only (see Section 4 — this file is in the forbidden write list)

## 1. Purpose

Agents operating on this repo generate and maintain documentation for Aspose FOSS products.
All content must be grounded in evidence from the knowledge model. This file is the
authoritative source of operating rules for all agents.

## 2. Read Order (always read in this order before doing any work)

1. This file (AGENTS.md)
2. Agent instructions file (`CLAUDE.md`, `CODEX.md`, or `.kilocode/rules-code/`) — if present
3. `knowledge/{family}/{platform}/model.yaml` — for the target product
4. `knowledge/{family}/{platform}/claims.md` — verify claims are current
5. `knowledge/{family}/{platform}/merged/api_surface.md` — for API grounding (human-readable, generated by promote.py)

New contributor or agent? See the `getting-started` skill for step-by-step fresh-clone setup.

## 3. Mental Model Refresh Protocol

Before editing any content page for family/platform X:

1. Read `knowledge/{family}/{platform}/model.yaml`
2. If `stale_since` is not null → the knowledge model is outdated; do not edit content until
   a knowledge-diff (S-12) and knowledge-update (S-14) have been run
3. Read `claims.md` and `api_surface.md` for the product
4. Only then proceed to content tasks

## 5. Evidence Requirements (non-negotiable)

- Every content page write must pass S-23 (content-check) before committing.
  **S-23 implementation**: `python scripts/pipeline/audit.py --files {path}` (deterministic, scriptable).
  Pre-commit hook enforces this automatically; CI workflow blocks PRs with FAILs.
- Every code block in `content/` must come from a snippet in `knowledge/{family}/{platform}/snippets/`
- Every factual claim must be traceable to a `claim_id` in `knowledge/{family}/{platform}/claims.json`
- Claims with `confidence < 0.5` require human review before use
- An `evidence:` YAML frontmatter block must be present in every content page. Generate it
  deterministically with `python scripts/pipeline/attach_evidence.py --files {path}` (for pages
  with code blocks) or manually via S-24 (evidence-cite, for prose-only pages). Format:
  ```yaml
  evidence:
    model_sha: "<repo_sha from merged/model.yaml>"   # anchors to knowledge version
    model_version: "<version>"
    claims: [CLM-xxx, ...]      # claim_ids from merged/claims.json ([] is valid)
    apis: [ClassName.method, …] # verified against merged/api_surface.json ([] is valid)
    formats: [{ext: glb, support: both}, …]  # omit if no format content
  ```
  Do **not** include `ground_check:` — it is self-reported and unverifiable.
  Do **not** use inline HTML comments (`<!-- evidence: ... -->`).
  Frontmatter is the canonical citation store, machine-validated by `audit.py`. The
  `evidence-panel` Hugo partial renders this data **only in non-production builds**
  (see Section 13 — Internal Metadata Rendering Policy). After any knowledge model update,
  rerun `attach_evidence.py {family} {platform}` to refresh stale blocks.

## 6. Skill Chains by Task

Skills are the **only sanctioned execution mechanism** for the task types listed below.
When your requirement matches a listed task type, you must follow the corresponding chain —
invoking each skill in order, passing outputs forward, and not substituting manual reasoning
for any step that has a registered skill. If your requirement does not match any listed task
type, follow the protocol in §6b before doing anything else.

### Initial generation (new page)

```
S-10 (project-phase-store) → S-18 (page-plan) → S-19 (page-draft) → S-22 (faq-generate)
→ S-23 (content-check / audit.py) → S-38 (truth-audit, deep) → S-24 (evidence-cite) → S-01 (path-guard) → write
```

### Knowledge bootstrap

```
S-34 (repo-scout) → S-37 (knowledge-enrich) → S-35 (truth-merge) → S-31 (truth-index)
```

### Maintenance (repo changed)

Resolve repo path first:
```bash
repo_path=$(python scripts/pipeline/core/clone_cache.py resolve {family} {platform})
```

Then run the chain:
```
S-12 (knowledge-diff {family} {platform} $repo_path)
→ S-13 (stale-detect)
→ S-14 (knowledge-update {family} {platform} $repo_path)
→ S-20 (page-update) → S-23 (content-check / audit.py) → S-24 (evidence-cite) → S-01 → write
```

### Enhancement (below rubric quality)

```
S-17 (rubric-align) → S-21 (page-enhance) → S-23 → S-01 → write
```

### Healing (grade D or below)

```
S-25 (eval-page) → S-26 (heal-page) → S-23 → S-25 → S-01 → write (or escalate)
```

### Batch reference page generation

```
batch-reference → /truth-audit (spot-check) → S-24 (evidence-cite) → S-01 (path-guard) → write
```

Platform scope rules enforced by `batch-reference`:
- **cpp / python**: concrete classes only (skip `^I[A-Z].*` abstract types and known C++ base classes); enums included
- **java / net**: interfaces, concrete classes, structs, and enums all included
- **Idempotency**: existing pages are never overwritten; re-runs skip already-present slugs

## 6a. Skill-First Execution Mandate

### Rule

Every agent operating on this repo must treat the skill system as the **default and required**
execution mechanism. This rule has the same enforcement weight as path-guard (§4) and
evidence requirements (§5).

### What "skill-first" means in practice

1. **Before starting any task**, identify which registered skill(s) in §12 cover it.
2. **Invoke matching skills** in the order defined by §6 chains. Do not perform equivalent
   work through inline reasoning, shell one-liners, or ad hoc prompting when a skill exists.
3. **Activate upstream dependencies automatically.** If a skill you need requires a
   precondition (e.g., `/knowledge-bootstrap` before `/page-draft`), you must invoke that
   precondition skill first — even if the user's request did not mention it.
4. **Do not invent workflows.** If no skill covers the requirement, follow §6b (gap
   escalation). Do not design a one-off process and execute it.

### Dependency Activation Rule (DAR)

Agents must activate the upstream skill if it has not already been confirmed as passing in
the current session. "Passing" means: the upstream skill returned a non-STOP status in
this conversation, no knowledge-modifying skill has run since, and less than one hour has
elapsed.

| Downstream skill | Required upstream | Trigger condition |
|-----------------|------------------|------------------|
| `/page-plan` (S-18) | `/knowledge-bootstrap` | Always |
| `/page-draft` (S-19) | `/knowledge-bootstrap` | Always |
| `/page-draft` (S-19) | `/page-plan` (S-18) | Plan not in session context |
| `/page-update` (S-20) | S-12 `/knowledge-diff` + S-14 `/knowledge-update` | `stale_since` not null |
| `/page-enhance` (S-21) | S-25 `/eval-page` or S-17 `/rubric-align` | Eval not in session context |
| `/heal-page` (S-26) | S-25 `/eval-page` | Eval not in session context |
| `/content-check` (S-23) | `/knowledge-bootstrap` | Always |
| `/truth-merge` (S-35) | S-34 `/repo-scout` | Scout output absent |
| `/batch-remediate` (S-40) | `/knowledge-bootstrap` | Always |
| `/batch-eval-fix` (S-41) | `/knowledge-bootstrap` | Always |
| `/faq-generate` (S-22) | `/knowledge-bootstrap` | Always |
| `/new-docs-page` (S-56) | `/knowledge-bootstrap` | Always |
| `/new-blog-post` (S-57) | `/knowledge-bootstrap` | Always |
| `/new-kb-howto` (S-58) | `/knowledge-bootstrap` | Always |
| `/new-kb-faq` (S-59) | `/knowledge-bootstrap` | Always |
| `/new-reference-page` (S-60) | `/knowledge-bootstrap` | Always |
| `/new-products-page` (S-61) | `/knowledge-bootstrap` | Always |
| `/batch-reference` (S-62) | `/knowledge-bootstrap` | Always |
| `/change-guard` (S-33) | `/knowledge-bootstrap` | Always |
| `/content-audit` (S-32) | `/knowledge-bootstrap` | Always |
| `/site-plan` (S-47) | `/knowledge-bootstrap` | Always |
| Any content write | S-01 `/path-guard` | Always (final gate) |

If the upstream skill returns `STOP` or `DENY`, halt immediately and report. Do not continue
to the downstream skill.

**DAR scope**: The DAR table lists skills that require an upstream dependency to be
activated *before* they can begin. Orchestrator skills that invoke upstream dependencies
as part of their own internal pipeline (e.g., `launch-product` invoking bootstrap as
Stage 0, `knowledge-update` managing the full refresh chain) are not listed — they manage
their own dependency chain. The test is: "Does this skill require someone else to have
already run the upstream skill?" If yes → DAR entry. If the skill runs the upstream
itself internally → no DAR entry.

**DAR maintenance**: When a skill is added, removed, renamed, or split, update this table.
Run `python scripts/ci/check_dar_coverage.py` to verify alignment between the DAR table
and skill file preconditions.

## 6b. Capability Classification and Gap Escalation

Before starting any task that is not a direct invocation of a single registered skill, the
agent must classify its capability level and act accordingly.

### Capability states (choose exactly one)

| State | Definition | Required action |
|-------|-----------|----------------|
| **FULL** | Every step of the requirement is covered by a registered skill in §12 | Invoke the skill chain; no gap report needed |
| **PARTIAL** | Some steps are covered; others are not | Execute skill-covered steps; produce gap escalation report for uncovered steps; do not perform uncovered steps through ad hoc work |
| **NONE** | No registered skill covers this requirement | Do not start work; produce gap escalation report immediately; await human decision |
| **BROKEN** | A required skill exists but fails when invoked | Invoke it, capture failure output; produce breakage report; do not bypass; await human decision |

### Classification output

When starting a novel, multi-part, or ambiguous request, state:

```
CAPABILITY ASSESSMENT — {brief task description}
State: FULL | PARTIAL | NONE | BROKEN
Skill(s) covering this task: [list skill IDs and names, or "none"]
Gap (if PARTIAL or NONE): [describe what is not covered]
Broken skill (if BROKEN): [skill ID, invocation attempted, error observed]
Planned action: [what you will do next]
```

For requests that are direct invocations of a single skill or a predefined §6 chain, this
output is implicit — you do not need to print it.

### Gap escalation report format

When state is PARTIAL or NONE, produce this report after completing any skill-covered work,
and save to `reports/skill-gaps/{YYYY-MM-DD}-{task-slug}.md`:

```
SKILL GAP ESCALATION
Task: {what was requested}
Capability state: PARTIAL | NONE
Skills invoked (completed): [list]
Uncovered requirement: {precise description}
Impact: {what the user won't get until this gap is filled}

ENHANCEMENT PLAN
  Title: {short name for the missing skill}
  Proposed skill ID: {next available S-xx or descriptive name}
  Input: {what the skill would receive}
  Output: {what the skill would produce}
  Skill file location: skills/{proposed-name}.md
  Depends on: {upstream skills it would call}
  Estimated complexity: LOW | MEDIUM | HIGH
  Workaround available: YES | NO
  If YES — workaround description: {only if it can be done safely without fabrication}
```

### Broken skill report format

When state is BROKEN, save to `reports/skill-breakage/{YYYY-MM-DD}-{skill-id}.md`:

```
SKILL BREAKAGE REPORT
Skill: {ID and name}
Invocation: {exact command or invocation attempted}
Expected output: {what the skill's spec says it should produce}
Actual output / error: {verbatim failure output}
Impact: {what tasks are blocked until this is fixed}
Suggested diagnosis: {most likely cause based on the error}
```

### Novel requirement protocol

If the requirement does not match any task type in §6:

1. Classify capability (FULL / PARTIAL / NONE) — for truly novel requirements this will
   usually be PARTIAL or NONE.
2. If PARTIAL: execute skill-covered steps, then produce gap escalation report.
3. If NONE: produce gap escalation report immediately. Do not attempt the work.
4. Do not design a new workflow and execute it inline — this is prohibited by §11.
5. Fill in the "Enhancement Plan" section of the gap escalation report fully. This is the
   mechanism by which the skill system grows to cover new requirements.

## 7. Hard Stop Conditions

The following always cause immediate halt (no agent override):

- S-01 path-guard returns `DENY`
- S-23 content-check returns `FAIL` after 2 retries
- `knowledge/model.yaml.api_confidence = "low"`
- Page grade = F (critical finding) from S-25
- Agent classifies requirement as NONE (no skill covers it) and proceeds with ad hoc work —
  unconditional STOP; produce a gap escalation report (§6b) instead
- A required upstream skill (per DAR table in §6a) returns `STOP` or `DENY` — do not
  proceed to the downstream skill; report the blocking condition to the user

## 8. Escalation Conditions (route to human review)

- S-23 `FAIL` persists after remediation
- S-12 diff reveals removed public class or changed method signature
- `stale_report` shows > 30% of page claims are orphaned
- Heal loop (S-26) fails to improve grade after 2 attempts
- Skill breakage report is filed (§6b) — a broken skill cannot be bypassed; human must
  diagnose and repair the skill before affected task types can proceed

## 9. Maintenance Workflow

**Trigger**: `knowledge/model.yaml.stale_since` is not null (repo has changed)

1. S-12 (diff) — identify which files changed
2. S-13 (stale-detect) — which content pages are affected
3. For each affected page: S-14 → S-20 → S-25
4. S-15 (embed-knowledge) — sync vector store if used
5. Commit: `knowledge/` changes + `content/` changes together

## 10. Evidence Proof in Commits

Every commit touching `content/` MUST include in the commit message:

- Knowledge model SHA: `knowledge/{family}/{platform}/model.yaml` `repo_sha` value
- Ground-check result: `PASS` (with report path)

## 10b. Content Provenance Rules

Every `.md` content file carries a `provenance:` block in its YAML frontmatter.
This block is **internal metadata** — never rendered in Hugo templates.

### Provenance fields

```yaml
provenance:
  content_origin: skill-generated | agent-drafted | human-authored | unknown
  translation_origin: translator-batch | translator-sync | translator-page | translator-retranslate | agent-translated | human-translated | unknown
  source_file: <relative path of English source>   # locale files only
  source_sha: <first 12 hex chars of SHA-256 of English source>  # locale files only
  last_mechanism: translator | evidence-attach | grade-writer | fixer | skill | agent-edit | human-edit | unknown
  auto_updatable: true | false
  reviewed: true | false
```

### Lifecycle rules

| Event | Fields updated |
|-------|----------------|
| Translator produces a new or updated locale file | `translation_origin`, `source_file`, `source_sha`, `last_mechanism: translator`, `auto_updatable: true`, `reviewed: false` |
| Evidence attachment writes evidence block | `last_mechanism: evidence-attach` only — all other fields unchanged |
| Grade writer writes grade block | `last_mechanism: grade-writer` only — all other fields unchanged |
| Remediation fixer modifies content | `last_mechanism: fixer` only — all other fields unchanged |
| Skill generates a new English page | `content_origin: skill-generated`, `last_mechanism: skill`, `auto_updatable: true`, `reviewed: false` |
| Human edits content | `last_mechanism: human-edit`, `auto_updatable: false`, `reviewed: true` |
| Agent edits content directly | `last_mechanism: agent-edit`, `reviewed: false` |

**Critical:** Evidence attachment, grade writes, and fixer runs are metadata-only operations. They MUST update `last_mechanism` but MUST NOT change `auto_updatable` or `translation_origin`.

### Overwrite/skip decision rules

The translator sync command uses `auto_updatable` to decide whether to overwrite an existing locale file:

```
locale file does not exist → translate (new file)
locale file exists AND auto_updatable == true → translate (overwrite)
locale file exists AND auto_updatable == false → skip, log reason
```

**The git commit author email is NOT a reliable provenance indicator and MUST NOT be used for overwrite decisions.** The `_is_bot_authored()` function was removed in commit `cdaa1daac`. Do not recreate it.

### Interpreting unknown provenance

`translation_origin: unknown` and `content_origin: unknown` are set by the backfill migration on pre-existing files. This means **origin is unverified**, not that the file is safe to overwrite. Use `auto_updatable` to make overwrite decisions — it is set to `true` by the backfill for all existing files, which is the correct conservative default.

### Protecting a file from automated overwrite

Set `auto_updatable: false` in the file's provenance block. The translator sync will log `[SKIP] ... -- auto_updatable=false, requires review` and skip the file.

### Staleness detection

`source_sha` holds the first 12 hex characters of SHA-256 of the English source content at the time of translation. If `source_sha` does not match the current English source, the locale file is stale and eligible for re-translation (if `auto_updatable: true`).

### Backfill

`scripts/pipeline/provenance_backfill.py` writes provenance to all existing files that lack it. It is idempotent and safe to re-run. Files that already have a provenance block are skipped.

## 11. Prohibited Actions

- Copy content from `golden/` corpus into `content/` pages (`golden/` is rubric reference only)
- Write API method names not present in `knowledge/{family}/{platform}/merged/api_surface.md`
- Write format claims not present in `knowledge/{family}/{platform}/formats.md`
- Generate code blocks using LLM — all code must come from `snippets/`
- Skip S-23 content-check for any reason
- Write to forbidden paths listed in Section 4
- Bypass a registered skill by performing its equivalent function through manual reasoning,
  inline shell commands, or ad hoc prompting — even if the output appears correct
- Perform any step of a requirement classified as PARTIAL or NONE without first producing a
  gap escalation report (§6b) and receiving explicit human approval for the uncovered portion
- Invent a new workflow or process for a requirement type not covered by §6 — produce the
  gap escalation report and enhancement plan defined in §6b instead, then halt

### Environment & Dependencies

**Rule: all scripts must load environment variables exclusively from `.env` via `core.env_loader`.**

#### Virtual environment (.venv)

**Rule: always use `.venv` for all Python execution. Never use system Python directly.**

The repo contains a pre-configured virtual environment at `.venv/` (repo root) with all
required packages already installed (tree-sitter, pyyaml, requests, python-dotenv, pytest).
Always activate it before running any script or `pip install` command.

**Activate:**
```bash
# Windows (Git Bash / WSL)
source .venv/Scripts/activate

# Unix / macOS
source .venv/bin/activate
```

Once activated, `python` and `pip` resolve to the venv — no path prefix needed.

**Before installing any package** — check whether it is already in `.venv`:
```bash
pip show <package>          # with venv active
```

Install only into `.venv`, never into system Python. All `pip install -r` commands in this
file assume the venv is active.

**Agents must not** run `python` or `pip` commands without first confirming `.venv` is
active (`echo $VIRTUAL_ENV` should be non-empty). For automated skill chains, prepend
`source .venv/Scripts/activate &&` (Windows) or `source .venv/bin/activate &&` (Unix)
to any shell command that invokes Python.

#### `env_loader` — automatic dotenv loading

`scripts/pipeline/core/env_loader.py` provides `load_env()`. Every CLI entry point calls it
once at startup, before any `os.environ.get()` call:

```python
from core.env_loader import load_env
load_env()
```

Behaviour:
- Reads `.env` at repo root into `os.environ`
- Uses `override=False` — shell-exported variables and CI secrets always take precedence
- No-op (silent) if `python-dotenv` is not installed or `.env` does not exist

**Agents must not** call `os.environ.get()` without first ensuring `load_env()` has been called
in the entry point. For new scripts, add the standard two-line block immediately after the
`sys.path` setup section.

## 13. Internal Metadata Rendering Policy

The `evidence:` frontmatter block is **internal provenance data** that must never appear
on the public-facing website. It exists solely for pipeline validation and debugging.

### Design

The `layouts/partials/evidence-panel.html` partial is gated in all four public-facing
theme base templates (`products`, `docs`, `kb`, `blog`) with:

```html
{{- if ne hugo.Environment "production" }}{{- partial "evidence-panel.html" . -}}{{- end }}
```

This means:

| Build context | `hugo.Environment` | Panel renders? |
|--------------|-------------------|----------------|
| CI production build (`--environment production`) | `"production"` | **No** |
| CI staging build (`--environment staging`) | `"staging"` | Yes (QA only) |
| Local `hugo server` | `"development"` | Yes (dev only) |
| Plain local `hugo` (no `--environment` flag) | `"production"` (default) | **No** |

### CI workflow requirement

All site build workflows in `aspose.org-workflows` **must** pass
`--environment "${{ github.event.inputs.environment }}"` to the `hugo` build command.
This ensures the `workflow_dispatch` `environment` input (already used for deploy targeting)
is also forwarded to Hugo's template context. All 7 site workflows already do this.

If a new site workflow is added, the same flag is required on the `hugo` build step.
Omitting it is safe (Hugo defaults to `"production"` → panel hidden) but must be explicit.

### What must not change

- The `evidence:` frontmatter block must remain in content files — it is required by
  `audit.py`, `attach_evidence.py`, and `evidence_depth.py` for validation and staleness
  detection. Do not remove or relocate it.
- Do not call `evidence-panel.html` unconditionally from any base template. The partial
  itself contains a comment warning against this.
- Do not gate the panel on URL patterns (e.g. `-qa.aspose.org`) — the `hugo.Environment`
  mechanism is the correct and durable approach.

## Operating Standard

Every agent operating on this repository is expected to behave as a disciplined user of a
governed skill system — not as an autonomous reasoner inventing its own processes. The skill
system is the documented, human-reviewed record of how content work is done here. When skills
cover a requirement, they must be used. When they do not, the gap must be reported and
recorded so the skill system can grow. An agent that silently bypasses skills, fabricates
workflows, or completes tasks partially without disclosure violates the operating contract of
this repository regardless of whether the output appears correct. Correctness of output does
not retroactively legitimize non-compliant process. The test is not "did it work?" — the test
is "did it work through the skill system, with the skill system's evidence and path rules
intact?"
